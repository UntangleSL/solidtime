## Layout and Interaction Contract

### 0. What the UI receives (advisory field names)

Every field is owner-only; an impersonating admin gets none of them (D-14).

- **Per linked time entry in view**, next to the existing `linkedTimeEntryIds`:
  - `sync_flags[time_entry_id]`: `{ kind: 'moved' | 'cancelled' | 'removed', meeting_start, meeting_end, new_start|null, new_end|null, subject }`.
    - `meeting_*` is the recorded snapshot (D-01). `new_*` is filled only for `moved`.
    - Only entries whose recorded start is in the future or within the last 60 days are included (D-10).
  - `auto_adjusted[time_entry_id]`: `{ at, from_start, from_end }`, present for 7 days after a silent D-04 adjust **(default: 7 days)**.
- **Counter** (whole flagged window, not just the view, D-11): `{ count, first: { time_entry_id, start } | null }`. "First" is the flagged entry with the earliest current entry start.
- **Per meeting occurrence (D-03)**: `moved_from: { time_entry_id, entry_start, entry_end }` when a started meeting moved to this slot and its link still points to the old entry. `null` otherwise.

### 1. Out-of-sync marker on the entry block (D-08, OSYNC-03)

**Placement.** In the core `event-extra` slot (title row of `FullCalendarEventContent`, `flex items-center gap-1`), order: Phase 4 origin icon `CalendarDays`, then the marker, then the title. `Calendar.vue` renders `<OutlookEntryBadge>` and `<OutlookSyncFlagMarker>` in that slot. The marker is rendered only when the entry has a flag and `canAct` is true.

**Look.** `TriangleAlert`, 12px (`size-3 shrink-0`), `text-amber-700 fill-amber-100 dark:text-amber-300 dark:fill-amber-950`, `cursor-pointer`. One icon for all three reasons: the reason is in the text, and the shape stays recognisable at 12px **(default)**. No other change to the block (fill, border, opacity and size are core and stay as they are).

**Hover text.** Native `title` on the marker, the same mechanism as the Phase 4 origin icon and the core misplaced-break hint. It is drag-safe and needs no layer inside a draggable block. Two lines:
1. The reason (`syncFlagReason.ts`):
   - moved: "Meeting moved in Outlook: Tue 10:00 – 11:00 → Wed 12:00 – 13:00"
   - cancelled: "Meeting cancelled in Outlook"
   - removed: "Meeting removed from Outlook"
2. "Click to review"

Range format:
- Use the weekday only ("Tue 10:00 – 11:00") when the old and new dates fall in the same week. Otherwise use "Tue, Nov 24 · 10:00 – 11:00".
- Times follow the organization's `time_format` (12-hour gives "10:00 AM – 11:00 AM").
- Dates use the panel's date format and locale.

**Click.**
- `@pointerdown.stop` and `@click.stop` on the marker, so the core block never starts a drag or opens the edit modal from it. The click opens the resolve popover (section 2) anchored to the entry block.
- Clicking anywhere else on the block keeps the core behaviour (edit modal, drag, resize).
- The marker is NOT focusable and has no role. A real button nested in the block's `role="button"` would break its semantics (Phase 5 rule). The keyboard paths are the context menu (section 2) and the toolbar counter (section 3).

**Accessible description.** The core block's `aria-label` (its title) hides inner text. So the marker renders a hidden span (`hidden`, with an `id`) holding "Out of sync with Outlook. <reason>." On mount, `describeBlock.ts` adds that id to the closest `[data-event-id]` element's `aria-describedby`, and removes it on unmount. This is the same DOM-hookup pattern as `labelDialogBySubject` in `OutlookGhostDetail`. The Phase 4 origin text (`from_meeting`) switches to the same mechanism, so a screen reader hears, for example, "Weekly sync, button. Created from an Outlook meeting. Out of sync with Outlook. Meeting cancelled in Outlook."

`data-testid="outlook-sync-flag-marker"`, `data-flag-kind="moved|cancelled|removed"`.

### 2. Resolving a flag: the resolve popover (D-04, D-05, D-08)

**Entry points** (all only when `canAct`):

| Entry point | Behaviour |
|-------------|-----------|
| Click on the marker | Opens the popover anchored to the entry block |
| Entry context menu (right-click, Shift+F10 or the context-menu key on a focused entry) | First item `TriangleAlert` (16px, amber classes as the counter) "Review Outlook change", then a `ContextMenuSeparator`, then the core items (Edit, Duplicate, Split, Delete) unchanged. After the menu has closed (existing `afterMenuClosed` pattern), the popover opens anchored to the entry. Unflagged entries show the core menu exactly as today |
| Toolbar counter | Jump, then the popover opens (section 3) |

**Core seam (ledgered, additive):** `TimeEntryCalendar.vue` gains a `context-menu-entry-extra` slot with `{ timeEntry }`, rendered at the top of the completed-entry menu branch. The fork component renders nothing for unflagged entries, and it renders its own separator.

**Popover (`OutlookSyncFlagPanel`).**
- `Popover` with `PopoverAnchor :reference="blockEl"`, `PopoverContent` `side="right"`, `align="start"`, `sideOffset` 8, collision flipping on, `w-96 p-4`, non-modal.
- Labelled by its title (`aria-labelledby`).
- `data-testid="outlook-sync-flag-panel"`, `data-kind`, `data-anchor="entry|counter"`.

Content, top to bottom:
1. **Title** (13px 600, `id` for labelling), `outlook-sync-flag-title`:
   - moved: "Meeting moved in Outlook"
   - cancelled: "Meeting cancelled in Outlook"
   - removed: "Meeting removed from Outlook"
2. **Entry line** (12px 600 `text-primary`, `mt-1 truncate`, full text in `title`): the entry's description, else "No description" (core copy).
3. **Time list** (`mt-2 grid grid-cols-[auto_1fr] gap-x-2 gap-y-1`, 12px, `tabular-nums`; labels 400 `text-tertiary`, values truncate):

| Kind | Rows |
|------|------|
| moved | "Before" → recorded meeting range (400 `text-tertiary`); "Now" → new meeting range (600 `text-primary`); "Your entry" → the entry's current range (400 `text-secondary`) |
| cancelled / removed | "Meeting" → recorded meeting range (400 `text-secondary`); "Your entry" → the entry's current range, only when it differs from the meeting range |

   Ranges here always use the full form "Tue, Nov 24 · 10:00 – 11:00". Test ids: `outlook-sync-flag-before`, `outlook-sync-flag-now`, `outlook-sync-flag-entry`, `outlook-sync-flag-meeting`.
4. **Note** (12px 400 `text-tertiary`, `mt-2`), `outlook-sync-flag-note`:
   - moved: "You changed this entry's time, so it was not moved automatically."
   - cancelled / removed: "Nothing is deleted unless you choose to."
5. **Not-in-view line**, only when anchored to the counter (section 3 fallback): 12px `text-tertiary` "This entry is outside the days or hours shown."
6. `Separator` (`mt-4`), then the **footer** `mt-4 flex justify-end gap-2`:

| Kind | Left | Right (last) | Focus on open |
|------|------|--------------|---------------|
| moved | `SecondaryButton` "Keep as is" (`outlook-sync-flag-keep`) | `PrimaryButton` `CalendarSync` "Adjust to Outlook" (`outlook-sync-flag-adjust`) | "Adjust to Outlook" |
| cancelled / removed | `SecondaryButton` "Keep as is" | `Button variant="outline" size="default"` `Trash2` "Delete entry", label and icon `text-destructive` (`outlook-sync-flag-delete`) | "Keep as is" (never the destructive action) |

7. **Inline alert** (only after a failure): `role="alert"`, `mt-2 flex items-center gap-1`, 12px `text-destructive`, `CircleX` 12px, mapped reason (Copywriting), `outlook-sync-flag-alert`.

**Delete: inline confirmation, no undo (decision).**
- Toasts in this codebase cannot carry an action, and a deleted entry cannot be restored by the core API, so undo is not offered.
- "Delete entry" swaps the footer in place (no modal over the popover). The question goes on its own line: "Delete this time entry? This can't be undone." (12px 400 `text-secondary`). Below it, `flex justify-end gap-2`: `SecondaryButton` "Cancel" (`outlook-sync-flag-delete-cancel`), then `Button variant="destructive"` `Trash2` "Delete" (`outlook-sync-flag-delete-confirm`).
- Focus moves to "Cancel". Cancel and Esc return to the normal footer with focus on "Delete entry". A second Esc closes the popover.

**Per-action loading.** Pessimistic, because the popover is open and the user waits on it:
- The acting button shows its spinner and is disabled. `PrimaryButton` / `SecondaryButton` use `loading`; the destructive `Button` shows a 16px `LoadingSpinner` in place of `Trash2` and is `disabled`.
- The other footer button is disabled.
- The popover cannot be dismissed by outside pointer-down or Esc until the request settles (the same guard as `OutlookGhostDetail` `busy`).
- The marker gets `aria-busy` on the block (no visual change).

**Outcomes:**

| Action | Success: UI | Feedback | Focus after |
|--------|-------------|----------|-------------|
| Adjust to Outlook | Popover closes. Time-entry, flag and counter queries invalidate. The entry re-renders at the new times, possibly in another day or week, and its marker is gone | Success toast "Time entry adjusted to Outlook" with the message "Wed, Nov 25 · 12:00 – 13:00"; announcement "Time entry adjusted to Outlook" | Opened from the counter: the counter if it is still shown. Otherwise the moved entry block if rendered, else the counter, else the Sync button |
| Keep as is | Popover closes; the marker disappears; the entry is unchanged. A later, different Outlook change can flag it again (server rule) | No toast; announcement "Kept as is" | Opened from the counter: the counter if it is still shown, else the entry block. Otherwise the entry block |
| Delete (confirmed) | Popover closes. The entry leaves the calendar (core delete path; the link cascades away) and the counter updates | Core toast "Time entry deleted successfully"; announcement "Time entry deleted" | The counter if it is still shown, else the Sync button |

| Failure | UI |
|---------|----|
| Any action, generic, forbidden or validation (overlap included) | Popover stays open with values; inline alert with the mapped reason; error toast with title `osync_*_failed` and the reason as message; focus back on the acting button so a retry is Enter. The confirm footer stays in its confirm state after a failed delete |
| Stale (404 / 409: flag already resolved, entry deleted or changed in another tab) | Popover closes; queries invalidate; error toast "This entry changed in the meantime" with the message "The calendar was refreshed."; focus moves to the toolbar counter if it is still shown, else to the Sync button |

The anchor block re-renders (refetch, drag elsewhere) while the popover is idle: re-anchor to the block with the same `data-event-id` if it still exists; otherwise close silently. Starting a drag or resize on any entry closes an idle popover.

### 3. Toolbar counter "N out of sync" (D-09, D-10, D-11)

**Placement.** `OutlookSyncFlagCounter`, rendered by `OutlookCalendarControls` after the status and before `OutlookConfirmAll`: [status] [N out of sync] [Confirm N] [Sync], `gap-2`. It also renders in the reconnect state (resolving needs no Graph call) and in test-hook mode. It is not rendered when `canAct` is false or when the count is 0 (hidden, not disabled).

**Look.**
- Outline `Button size="sm"` (`h-8`) containing `TriangleAlert` (16px, `text-amber-700 dark:text-amber-400`) and the count.
- Below `md`: icon + count, for example "2" (`px-2`, `tabular-nums`).
- From `md`: icon + "2 out of sync".
- The count is the server's whole-window count (future plus the last 60 days, D-10/D-11), not only the visible days.
- `aria-label`: "2 time entries out of sync with Outlook. Show the first one." (singular: "1 time entry out of sync with Outlook. Show it.").
- Tooltip (300ms): "Show the first entry that changed in Outlook".
- `data-testid="outlook-out-of-sync"`, `data-count`.

**Click: jump to the first flagged entry.**
1. The target is `first` (earliest current entry start among flagged entries). Repeated clicks walk through the flags, because resolved ones leave the list.
2. If the target's day is a visible day of the current view: no navigation. Otherwise navigate to the target's date, keeping the view mode (week view goes to its week, day view to its day).
   - Core seam (ledgered, additive): `TimeEntryCalendar` exposes `goToDate(date)` through `defineExpose`, wired to `useCalendarNavigation`'s current date. `Calendar.vue` keeps a template ref and hands a navigator to the Outlook context.
   - A full page visit (`?date=`) is not acceptable: it reloads the page and loses state.
3. Wait for the time entries of that range (and the flags) to load. Then find `[data-event-id="<id>"]` and call `scrollIntoView({ block: 'center' })`, smooth only without `prefers-reduced-motion`. Focus the block with `preventScroll`, then open the resolve popover anchored to it (`data-anchor="entry"`). Focus goes into the popover per the section 2 table.
4. **Fallback:** the block is not rendered within 3s of the data settling. This covers a weekend day with weekends hidden, an entry outside the visible hours, or a slow load. The popover then opens anchored to the counter (`side="bottom"`, `align="end"`, `data-anchor="counter"`) with the "outside the days or hours shown" line, so the flag can still be resolved.
5. While the jump is in progress, the counter shows `aria-busy="true"` and ignores further clicks. There is no spinner (navigation is normally instant).

**Refresh.** The counter refetches after any Outlook sync, any resolve action, a D-03 move, and whenever the core `timeEntries` queries are invalidated. A core edit, drag or delete can change or clear a flag server-side.

### 4. Started meeting moved: "Move my entry here" (D-03)

The meeting occurrence with `moved_from` is a normal suggestion block at its new slot: same tiers, accent look, pre-assigned project line if Phase 5 applies. There is no extra visual on the block. Its `aria-label` gains the suffix ", already logged on Tue, Nov 24" (before the selected / dismissed suffixes). `data-moved-from` attribute on the block for tests. The old entry is never flagged (D-02) and shows no marker.

**Panel (`OutlookGhostDetail`).** An `OutlookMovedMeeting` block (`mt-4 space-y-2`, `data-testid="outlook-moved-block"`) goes after the pre-assignment block (or after the summary and link when there is none), above the separator:
1. **Eyebrow** (12px 400 `text-tertiary`, `flex items-center gap-1`): `CalendarClock` 12px + "Moved in Outlook · Already logged".
2. **Body** (12px 400 `text-secondary`, `tabular-nums`, `id` used by the button's `aria-describedby`): "You logged it on Tue, Nov 24 · 10:00 – 11:00. Create a new entry for this session, or move that one here." The range is the old entry's current times.
3. **Action:** outline `Button size="sm"` `MoveRight` "Move my entry here" (`outlook-detail-move-entry`), left-aligned.

It is placed in the body, not the footer, by decision. With the More actions button, a third footer button overflows `w-96` in Spanish ("Mover mi registro aquí" plus "Crear registro de tiempo" is about 385px against 308px free). The footer stays exactly as in Phase 5:
- [More actions] … [Create time entry], or [Edit] [Confirm] for a pre-assigned meeting.
- Dismiss / Restore stay in More actions.
- "Create time entry" / "Confirm" stays the primary default (a second entry for the new session, D-03).
- Focus on open is unchanged.

**Hover card.** One note line after the summary (and pre-assignment), before the hint: 12px 400 `text-tertiary`, `mt-2 flex items-center gap-1`, `CalendarClock` 12px + "Moved in Outlook. You logged it on Tue, Nov 24." (`outlook-hover-moved-note`). Hover-card actions are unchanged: the card stays light, and the move lives in the panel and the menu.

**Meeting context menu.** After "Create time entry" (or after Confirm + Edit for a pre-assigned meeting): `MoveRight` "Move my entry here". It has a trailing hint with the old date (`ml-auto` 12px `text-tertiary` `tabular-nums`, "Tue, Nov 24") (`outlook-menu-move-entry`). The rest of the menu is unchanged.

**Move behaviour.**
- The existing linked entry takes the meeting's new start and end through the core update path. Description, project, task, tags and billable are unchanged. The link now covers this occurrence.
- No confirmation: nothing is deleted, the old range is shown in the panel before the click and in the success toast afterwards, and the entry can be edited back.
- Pending:
  - From the panel: the button `loading`; "Create time entry" / "Confirm" and More actions are disabled; the panel cannot be dismissed.
  - From the menu: the menu closes; the block gets `aria-busy="true"`, `cursor-progress` and a 12px `LoadingSpinner` before the subject (the Phase 5 pending rule).
- Success:
  - The meeting leaves the lane (it is linked now) and the entry appears at the new slot (both queries invalidate).
  - Success toast "Time entry moved here" with the message "From Tue, Nov 24 · 10:00 – 11:00"; announcement "Time entry moved".
  - Focus goes to the moved entry block (`[data-event-id]`) if rendered, else the Phase 4 removal rule.
- Failure:
  - Panel: stays open, inline `role="alert"` line under the footer (the existing `outlook-detail-alert`), error toast "Could not move the time entry" with the mapped reason, focus back on the button.
  - Menu: the block returns to normal, error toast.
  - Stale (the old entry was deleted, or the link changed): toast "This entry changed in the meantime" / "The calendar was refreshed.", queries invalidate, and the occurrence then shows as a plain suggestion.

### 5. Silent auto-adjust feedback (D-04, D-12)

Decision: **no visual change on the block and no toast** **(default)**. The owner wants as few warnings as possible, and an entry that moves with its meeting is the expected outcome. The change stays discoverable in two quiet places:
1. **Origin icon tooltip.** For 7 days after the adjust, the Phase 4 origin icon's `title` (and its `aria-describedby` text) becomes two lines: "Created from an Outlook meeting" / "Updated from Outlook: Tue 10:00 – 11:00 → Wed 12:00 – 13:00". The range format is as in section 1. The badge gets `data-auto-adjusted` for tests.
2. **Announcement.** When a sync the user triggered or watched (week open) auto-adjusts entries in the current view, one polite announcement: "1 time entry updated from Outlook" / "3 time entries updated from Outlook". Adjusts made by the daily job are not announced. The user sees them through the tooltip only.

### 6. Keyboard and screen-reader summary

- **Keyboard paths:**
  - Tab to a flagged entry, then Shift+F10 / the context-menu key, then "Review Outlook change", then the popover (focus per section 2).
  - The toolbar counter (in the Tab order before Confirm N) jumps and opens the popover.
  - Enter on a D-03 meeting block opens the panel; Tab reaches "Move my entry here".
  - The menu also offers "Move my entry here".
- **Esc in the popover:** closes the delete confirmation first, then the popover. Focus returns to the entry block, or to the counter when the popover is anchored to it.
- **Live region** (existing polite `outlook-announcement`): "Time entry adjusted to Outlook", "Kept as is", "Time entry deleted", "Time entry moved", "N time entries updated from Outlook". Never on counter changes alone.
- **Reduced motion:** smooth scrolling and popover transitions only under `motion-safe:` / without `prefers-reduced-motion`.
- **Impersonation / `canAct` false:** no marker, no menu item, no counter, no moved block or note, no move item (D-14). The server sends no flags either.
