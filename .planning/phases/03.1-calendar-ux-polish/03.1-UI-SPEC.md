## DECISION D-04: how meeting blocks use the day column

### The question

Show the key meeting information at a glance AND make it obvious which side is "Outlook calendar" and which is "my time entries", without letting full-width meetings be mistaken for time entries.

### Options evaluated

| | A. Full width when free, lane only when an entry overlaps | B. Fixed wider lane (45-50%), no other cues | C. Always-on split (both halves reserved on EVERY day, divider, captions) | D. Stable half-lane on days that have meetings + wash + divider + header captions (CHOSEN) |
|---|---|---|---|---|
| Readability of a lone meeting | Best | Good | Good | Good (about 18 characters per subject line at 118px lane, 2 lines) |
| "Which side is Outlook" | Weak: same block is full width on one day and half on the next; no fixed zone | Medium: position only, nothing labels it | Strongest | Strong: fixed position + labelled + tinted zone |
| Layout stability | Poor: creating, dragging or resizing an entry flips meeting width, entry blocks jump | Stable | Stable | Stable per day: meetings are ALWAYS the right part of the column |
| Never hides/is hidden by an entry (D-01) | Needs re-flow logic on every drop, easy to violate | Geometric, trivially true | Geometric | Geometric (disjoint zones), no re-flow logic |
| Cost on days without meetings | none | none | Half the width wasted on every empty day (weekends, holidays) | none (empty days render exactly as upstream) |
| Fit with Phase 4 (meeting becomes an entry) | Entry appears over/beside meeting, shifts layout | Entry appears across from the meeting | Same | Entry appears directly across from the meeting: the left half fills up as meetings are assigned |
| Core change | High (per-cluster entry geometry) | Low (lane constant) | Medium (lane on every day) | Low (lane constant + 1 header slot) |
| Owner worry (full width is confusing) | Maximum exposure | Reduced | Removed | Removed |

### Decision

**Option D.** On every day that has at least one visible meeting, the day column is split: **left = "My time" (time entries, untouched), right = "Outlook" (meetings)**. The split is always the same rule on every such day, in week and day view, so the user learns it once. The Outlook lane is half the column in week view (wider than Phase 3's 30%) and a 260-420px panel in day view. Days with no meeting render exactly as upstream (full-width entries, no lane, no caption content).

Rationale:
1. The owner's own fear (full width is confusing) is the strongest signal; a solid blue block next to a solid project-coloured block is only unambiguous if position, label and style all agree. D gives three independent cues (zone, label, block style) instead of one.
2. Stable geometry. A lane that appears or resizes depending on what the user just dragged (Option A) makes entries and meetings jump during editing; the calendar is first an editing surface.
3. Half the column is enough to read: at the 1920px reference width a week has 7 columns of about 237px (lane 118px) or 5 columns of about 330px (lane 165px) when weekends are hidden (UX-01), 12px text, subject on 2 lines. That is the readability jump the owner asked for versus today's 30% lane at 10px with single-line truncation.
4. It keeps the safety property by construction: entries and meetings occupy disjoint rectangles, so nothing can hide anything (D-01/D-23), and CAL-02 needs no new pointer logic.
5. Phase 4 benefit: a meeting converted to an entry lands opposite itself.

Known trade-off, accepted: on a day that only has meetings the left half is empty. It is not wasted: it is the slot-selection area for logging time (empty left half = "nothing logged yet", which is exactly the product's core value moment).

### Day column geometry (exact)

Let `W` = day column width. The Outlook layer is the existing `overlay` slot child positioned `absolute inset-y-0 right-0.5`.

| | Week view | Day view |
|---|---|---|
| Lane width (`overlayLaneWidth` returned by `dayOverlayLane`) | `min(max(88px, 50%), calc(100% - 52px))` | `min(420px, max(260px, 38%))` |
| Entries container `right` (core, unchanged formula) | `calc(<lane> + 4px)` (2px default edge + 2px gap) | same |
| Entries container `left` | `left-0.5` (2px); with activity status: 8px (week) / 204px (day), unchanged | same |
| Lane inner gutter | 2px each side (blocks inset `inset-x-0.5`) | same |
| Block gap | 2px between side-by-side blocks, 1px under every block (adjacent meetings stay visibly separate) | same |
| Min side-by-side column width | 56px | 56px |
| `maxColumns` | `clamp(floor((laneInnerPx) / 56), 1, 3)` | `clamp(floor((laneInnerPx) / 56), 1, 4)` |

Worked examples (week view): grid 1590px, 7 days: `W` 227, lane 113, entries area about 108, 2 columns max. 5 days (weekends hidden): `W` 318, lane 159, entries about 153, 2 columns. 1366px laptop, 7 days: `W` 147, lane 88, entries about 53 (functional, 1 column; hiding weekends is the recommended fix and the settings hint points at it). Day view 1500px: lane 420, entries about 1074 (minus 204 when activity status shows), up to 4 columns of about 100px+ (3 at 1366px).

`laneInnerPx` is measured with `useResizeObserver` on the layer element, so the column count adapts to the real pixel width and to sidebar collapse. `ghostLayout.ts` takes `maxColumns` as a parameter (default 3); `ghostLaneWidth(isDayView)` returns the two strings above.

### Zone cues (what makes the sides unmistakable)

1. **Position, always the same:** meetings are the right part of the day column; entries the left. Never swapped, never full width.
2. **Lane wash + divider:** the layer container carries a faint full-height background (`--m365-lane-bg`, 6% accent tint, translucent so grid lines stay visible) and a 1px solid left divider in `--color-border-tertiary`. The wash is `pointer-events-none`, so the empty part of the lane still starts a slot selection (CAL-02 stays true).
3. **Header captions (the legend):** under the weekday and date, a 16px caption row per day that has a lane: left "My time", right "Outlook" with a `CalendarDays` icon in the bar colour (copy in Copywriting). Rendered in the sticky header, so it never overlaps a block while scrolling. Width contract below.
4. **Block style:** meetings are flat (no shadow), tinted, with a 3px bar and a time line carrying a `CalendarDays` icon. Entries keep their project colour, border and `shadow-card`. Two non-colour cues (zone, bar shape) plus the icon, so meaning never rests on hue alone (Phase 3 accessibility rule kept).
5. **Dismissed variant** differs again (no bar, dotted border, faded), see below.

Header caption alignment: the caption row sits inside `fc-col-header-cell` which has `px-2`; use `-mx-2` so its width equals the column, then `[flex-1 "My time"] [lane-width "Outlook" with border-l]`, where lane width is the same string as `dayOverlayLane(dayStr, isDayView)`. The row is `aria-hidden="true"` (the lane group already has an accessible name). When the Outlook cluster is active (connection state `connected` or `reconnect`) EVERY header cell reserves the 16px row (empty on days without a lane) so the header height does not change when navigating weeks. When the integration is off, not connected or impersonating, no row is rendered. Core seam: one additive named slot in the header cell, `day-header-extra`, scoped `{ dayStr, isDayView }`, filled by the fork like `day-overlay`.

### Overlap rules

- **Entry vs meeting:** never overlap (disjoint rectangles). A meeting and an entry at the same time are visible side by side at the same vertical position. Neither is ever covered. Entries stay draggable, resizable, editable; the entries container is the only thing that changes width (as today).
- **Meeting vs meeting:** greedy columns inside the lane, `columns = min(needed, maxColumns)`. Columns are equal width. When more meetings overlap than `maxColumns`, the extras (in start order) share the last column and **cascade**: each extra gets `margin-left: 8px x depth` (depth 1..3, then stays at 3) and a 1px `--color-bg-primary` left edge so every block's left bar stays visible and clickable; later start paints on top. Hover or focus raises a block (`z-[1]`, still below the selection rectangle `z-[2]`, activity `z-10` and now line `z-50`). Everything stays reachable by keyboard (DOM order = start order).
- **Pointer rules (CAL-02, unchanged):** the layer container is `pointer-events-none`; each block is `pointer-events-auto` with `data-calendar-overlay`. The core `onSlotPointerDown` ignores `[data-calendar-overlay]`; blocks never carry `.fc-event`, `data-event-id`, `touch-none` or resizers. Blocks never start a selection, are never draggable. Wash, divider and caption are non-interactive (`pointer-events-none`, or in the header, no handlers).
- **Test hooks:** `data-testid="outlook-lane"` on the layer, `data-testid="outlook-lane-caption"` on the caption row.

## Spacing Scale

Declared values (multiples of 4):

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Gap between icon and text in blocks, lane right edge to entries (2px edge + 2px gap = 4px) |
| sm | 8px | Hover card row gap, cascade indent step, toolbar gaps |
| md | 16px | Hover card / settings padding (`p-4`), header caption row height |
| lg | 24px | Zoom button size (`size-6`) |
| xl | 32px | Toolbar control height (`h-8`) |
| 2xl | 48px | Time-axis width (existing `TIME_AXIS_WIDTH`) |
| 3xl | 64px | not used (reserved) |

Exceptions (dense time grid, same family as the entries it sits next to):
- Block internals use 2px / 3px / 6px (bar 3px, horizontal padding 6px after the bar, vertical padding 2px, gutters 2px, 1px gap under blocks) and a 14px text line height. These are sub-4 grid micro-values inherited from the calendar's existing 2px offsets (`left-0.5`, `right-0.5`); they are not layout spacing.
- Lane widths `88px`, `52px` (entries minimum), `56px` (minimum side-by-side column), `260px`, `420px` are all multiples of 4. The 50% / 38% shares are proportions.
- Block minimum height stays 16px; the 44px touch-target rule does not apply inside a time grid (keyboard path: Tab, Enter, Space). The two zoom buttons are 24px (WCAG 2.5.8 minimum), stacked vertically with 2px gap, because a horizontal pair does not fit the 48px axis cell at 24px each.
- Hover card width `w-72` (288px); detail panel stays `w-80`.

## Color

All colours are tokens or `color-mix()` of tokens. The fork defines ONE group of custom properties on `.m365-meeting` and `.m365-lane` (in the fork component's scoped style) so Phase 3.2 can re-skin the Outlook identity in one place:

```
/* light (default) */
--m365-meeting-bg:        color-mix(in srgb, rgb(var(--color-accent-500)) 16%, var(--color-bg-primary));
--m365-meeting-bg-hover:  color-mix(in srgb, rgb(var(--color-accent-500)) 24%, var(--color-bg-primary));
--m365-meeting-border:    color-mix(in srgb, rgb(var(--color-accent-600)) 35%, var(--color-bg-primary));
--m365-meeting-bar:       rgb(var(--color-accent-600));
--m365-meeting-text:      var(--color-text-primary);      /* subject */
--m365-meeting-text-2:    var(--color-text-secondary);    /* time, organizer */
--m365-lane-bg:           color-mix(in srgb, rgb(var(--color-accent-500)) 6%, transparent);
/* :root.dark .m365-meeting / .m365-lane */
--m365-meeting-bg:        color-mix(in srgb, rgb(var(--color-accent-400)) 22%, var(--color-bg-primary));
--m365-meeting-bg-hover:  color-mix(in srgb, rgb(var(--color-accent-400)) 30%, var(--color-bg-primary));
--m365-meeting-border:    color-mix(in srgb, rgb(var(--color-accent-400)) 40%, var(--color-bg-primary));
--m365-meeting-bar:       rgb(var(--color-accent-400));
--m365-lane-bg:           color-mix(in srgb, rgb(var(--color-accent-400)) 8%, transparent);
```

(`--color-accent-*` hold `r, g, b` triples, so they are wrapped in `rgb()`. The mixes are opaque because the second colour is opaque: this satisfies D-02 "solid fill". The grid shows through only in the lane wash.)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-default-background` | Grid surface, toolbar |
| Secondary (30%) | `bg-card-background`, `bg-popover`, `--color-bg-tertiary` | Panel, hover card, settings, header |
| Accent (10%) | `accent-500/600` light, `accent-400` dark, via `--m365-*` | Reserved list below |
| Destructive | not used | Dismiss is reversible; never styled destructive |

Accent reserved for (and nothing else):
1. The Outlook identity of a meeting block: its tint fill, its 3px side bar, and the lane wash (all through `--m365-*`).
2. The `CalendarDays` icon of the "Outlook" header caption (same bar colour).
3. The 2px ring of the meeting whose detail panel is open: `ring-accent-700` light / `ring-accent-200` dark (3.9:1 and 9:1 against the fill; a plain `accent-500` ring would vanish on the tint).
4. The spinning `RefreshCw` while a sync is in progress.
5. "Open in Outlook" link text and icon (panel, hover card has none, context menu uses neutral text).

Contrast (computed against the opaque fill, WCAG AA):
| Pair | Light | Dark |
|------|-------|------|
| Subject `text-primary` on fill | about 15:1 | about 11:1 |
| Time/organizer `text-secondary` on fill | about 8.9:1 | about 7.9:1 |
| Dismissed time/subject `text-secondary` on its lighter fill | above 9:1 | above 7:1 |
| 3px bar vs fill (non-text) | about 3.4:1 | about 5.9:1 |
| Bar vs plain grid | above 4:1 | about 5.9:1 |

Never apply `opacity` to meeting text. In dark theme the fill-versus-page contrast is low (about 1.3:1) by design (it is a tint, like Clockify's), so the bar and the tinted 1px border are the boundary cue (above 3:1).

Other colour rules:
- Entries keep their project colour, border and `shadow-card`; meetings never use project colours, the amber break hatch, or Microsoft brand blue.
- Known collision (accepted, mitigated by cues 1-4): a project whose colour is sky-like can sit beside a sky-tinted meeting. The meeting is flat, lighter, barred, in the labelled right zone; the entry is saturated, elevated, in the left zone. Planner: add a visual regression fixture with a sky-blue project.
- The existing sky activity-status strip (`rgba(14,165,233,…)`, 10px at the left edge of the column when activity data exists) is on the opposite side of the column from the lane and is unchanged.
- Warning marker, amber pair (`text-amber-600 dark:text-amber-400`), unchanged and only on `TriangleAlert`.

## Layout and Interaction Contract

### 1. Meeting block content (week and day view)

Structure (inside the block, `@container` named `meeting`): `flex flex-col px-1.5 py-0.5 overflow-hidden`, left padding measured after the 3px bar.

Content tiers by drawn block height `h` (px). Heights come from `minutesToPixels`, so zoom changes tiers automatically (at 100%: 15 min = 25px, 30 min = 50px, 60 min = 100px).

| Tier | Block height | Content (all lines truncate with ellipsis, subject clamps) |
|------|--------------|------------------------------------------------------------|
| T1 | `h` < 18 (the 16px minimum) | One line, `py-0`: subject. Trailing `Video` icon if online |
| T2 | 18 to 31 | One line: subject (+ trailing `Video`); inline start-end time appended after the subject only when the container is 150px or wider (`@[150px]`), otherwise subject only |
| T3 | 32 to 45 | Two lines: subject (1 line), then time line |
| T4 | 46 to 59, and any height above that in week view | Subject up to **2 lines** (`line-clamp-2`), then time line |
| T5 | 60 and above, **day view only** | T4 + organizer line (`User` 12px + name or "You are the organizer") |

Time line: `[CalendarDays 12px] 10:00 – 11:00 [Video 12px, right-aligned, only when online]`. Under a 96px container (`@container` max-width) show the start time only (`10:00`) so a two-column lane never wraps. In T1/T2 the leading icon is omitted (width is scarce); the bar, zone and caption carry identity there. Format via `formatTime(start, timeFormat)` in the user's timezone. Missing subject: "(No subject)". Tiers depend only on height; width only decides the inline time (T2) and the start-only time format.

Interaction and a11y (unchanged from Phase 3): `role="button"`, `tabindex="0"`, `aria-haspopup="dialog"`, `aria-expanded`, `data-calendar-overlay`, `data-ghost-id` (the existing attributes are reused, no new data attribute). Enter/Space opens the panel. The layer is `role="group"` with the day label, rendered only when the day has meetings.

### 2. Hover card (UX-03, D-05)

Built on reka `HoverCard` wrapped around the block, nested with the existing `Popover` trigger (both `as-child` on the same block element).

| Property | Contract |
|----------|----------|
| Open delay | 400ms. **Instant (0ms)** when the pointer moves to another meeting within 300ms of a card closing (keep a module-level `lastClosedAt`), so scanning across a week feels immediate |
| Close delay | 120ms (the card is hoverable: the pointer can enter it, required for Phase 4 actions) |
| Placement | `side="right"`, `align="start"`, `sideOffset` 8, `avoidCollisions` (flips left on the rightmost day), same anchor as the panel so click morphs card into panel in place |
| Size | `w-72 p-4`, `bg-popover border rounded-md shadow-md z-50` |
| Content | Eyebrow (12px `text-tertiary`): `CalendarDays` "Outlook meeting" ("Outlook meeting · Dismissed" when dismissed). Subject (13px 600, `line-clamp-3`, `break-words`). Time row `Clock` + `Tue, Oct 27 · 10:00 – 11:00 · 1h 00min` (midnight-spanning rule as in the panel). Organizer row (name, or "You are the organizer"). Online row `Video` "Online meeting" (not "Teams": no provider field, Phase 3 rule kept). Footer hint (12px `text-tertiary`): "Click for details". No location, attendees or body (D-20) |
| Reuse | One shared `OutlookMeetingSummary` component renders the rows for BOTH the hover card and the panel (eyebrow, subject, time, organizer, online, `meta` slot). The card adds the hint and an `actions` slot; the panel adds link, Separator and actions. Phase 4 puts "Create time entry / Assign to project" in the `actions` slot of both |
| Touch | Reka `HoverCardTrigger` ignores `pointerType === 'touch'`, so touch is click-only with no extra code. Hybrid devices follow the real pointer type |
| Close triggers | Esc, pointer leave (after close delay), a click on the block (the panel replaces it), any `pointerdown` elsewhere, a wheel or scroll event on the grid, a zoom step, a drag/resize/selection start, the context menu opening, a day or week change |

### 6. Zoom and scroll (UX-05, D-07)

**Mapping (decision):** zoom is the existing Grid Scale ladder. Zoom level = `slotMinutes` in the order 60, 30, 15, 10, 5, which equals 25, 50, **100** (default), 150, 300 px per hour, shown to the user as 25%, 50%, 100%, 150%, 300% (`100% = 100px/hour`). Reasons: `SLOT_HEIGHT` stays a constant 25px, so `useSlotSelection`, `useEventDrag`, `useEventResize`, `useCalendarGrid` and `useContextMenu` (all derive pixels from `slotMinutes`) need zero change and snap exactly at every level; the value persists in the same setting the popover already edits, so the popover's Grid Scale select and the zoom controls can never disagree. No new storage key.

| Input | Behaviour |
|-------|-----------|
| Plain wheel / two-finger scroll | Native vertical scroll of `.fc-scroller` (unchanged). No custom handling |
| Ctrl/Cmd + wheel over the grid or the time axis | `preventDefault` (non-passive listener on the scroller, via `useEventListener(scroller, 'wheel', fn, { passive: false })`), change zoom by one step. Accumulate `deltaY` and step when the accumulator reaches 48 (one mouse notch = about 100 = one step), at most one step per 100ms, reset the accumulator after 150ms idle. `deltaY < 0` zooms in (smaller `slotMinutes`), `> 0` zooms out |
| Trackpad pinch (Chrome, Edge, Firefox) | Arrives as a ctrlKey wheel: same path |
| Safari pinch | Arrives as `gesturechange`: best effort (Could), not covered by CI (no WebKit project): one step per scale change beyond 1.25 / 0.8. Ctrl/Cmd+wheel and the zoom buttons cover Safari |
| Zoom buttons | `+` and `-` in the header corner cell (above the time axis, as in the Clockify reference). Anchor = vertical centre of the visible grid |
| Settings "Grid Scale" | Unchanged; stays the precise and keyboard-accessible alternative |
| During drag, resize or slot selection | Zoom input is ignored (still `preventDefault` on ctrl-wheel so the page does not zoom); prevents corrupting in-flight pixel math |

Anchoring (keep the time under the pointer fixed): before the change compute `t = pixelsToMinutesFromMidnight(clientYToGridPixels(clientY))`; after the settings update and `nextTick`, set `scroller.scrollTop = max(0, minutesToPixels(t - startHour*60) - (clientY - scrollerRect.top))`. For the buttons use the scroller's vertical centre as `clientY`. At the min/max level the input does nothing (no bounce).

No refetch on zoom: `slotMinutes` lives in the object watched by `watch(calendarSettings, emitDatesChange, { deep: true })`; a zoom step must not emit a dates-change (compare only the date-affecting keys, or skip when only `slotMinutes` changed), otherwise every wheel notch refetches entries.

Visible zoom affordance:
- Header corner cell: two stacked icon buttons `size-6` (24px), `variant` ghost, icons `Plus` and `Minus` 12px, `aria-label` "Zoom in" / "Zoom out", `data-testid="calendar-zoom-in"` / `"calendar-zoom-out"`. At the end of the ladder the button uses `aria-disabled="true"` (keeps focus), muted. Tooltip (300ms): "Zoom in (Ctrl + scroll)" / "Zoom out (Ctrl + scroll)", with "⌘" instead of "Ctrl" on macOS (detect `navigator.platform` / `userAgentData`). This tooltip is where the wheel gesture is discoverable.
- Transient zoom pill: after any zoom change, a small pill "Zoom 150%" appears top-left over the grid (`absolute left-14 top-2 z-20`, `bg-primary text-primary-foreground rounded-md px-2 py-1 text-xs font-semibold tabular-nums shadow-dropdown`, `pointer-events-none`) for 1200ms then removed (fade 150ms under `motion-safe`, instant under reduced motion). `role="status"` `aria-live="polite"`, `data-testid="calendar-zoom-indicator"`.
- Hover cards close on any zoom step.

### 7. Sync cooldown (UX-06, D-08)

When a cooldown starts (what counts, see below), the connected-state Sync button shows a draining ring and a countdown, and tells the user in words when it is available again.

Which events start a visible cooldown:
| Event | Cooldown |
|-------|----------|
| Manual Sync completes (success or any settled answer) | 10s (existing `SYNC_COOLDOWN_MS`), `kind: 'manual'` |
| Any settled answer (manual or automatic) with status `throttled` or `unavailable` and `retry_after`, or a read that reports `retry_after` | `retry_after` seconds (never less than the manual 10s when the sync was manual), `kind: 'backoff'` |
| Automatic sync from week navigation completes OK | **none** (this is the UX-06 bug: today `extendCooldown(max(10s, backoff))` runs after every settled sync). The button is only unavailable while that sync is in flight (spinning) |
| Server throttles and the 10s floor | unchanged on the server |

Composable contract (fork `useOutlookMeetings.ts`): `extendCooldown` is called after a settled sync only when `target.force` is true or a back-off applies; the context additionally exposes `cooldownStartedAt: Ref<number>` and `cooldownKind: Ref<'manual' | 'backoff' | null>` (so the control can draw progress). `canSync`/`requestSync` semantics otherwise unchanged.

Button contract (`OutlookCalendarControls.vue`, connected state):
- **Use `aria-disabled="true"` (not the `disabled` attribute) during cooldown and while syncing**, handler returns early. Native `disabled` drops keyboard focus to `<body>` right after Enter on Sync; this keeps focus and still lets the tooltip show. Style with an `aria-disabled:` variant (muted, `cursor-not-allowed`), `data-testid="outlook-sync-button"` unchanged, plus `data-cooldown="manual|backoff"` while cooling.
- Idle: `RefreshCw` + "Sync Outlook" (unchanged). Syncing: spinning accent icon, `aria-busy="true"` (unchanged).
- Cooling down: the `RefreshCw` is replaced by a 16px SVG **progress ring** (radius 6, stroke 2, track `text-border` color at full circle, progress arc `text-text-tertiary`, draining counter-clockwise from full to empty over the cooldown; `motion-safe` linear 1s transition per tick, stepwise under reduced motion) and the label at `md` and up becomes "Sync in 8s" (`tabular-nums`, `sync_in` copy). The button keeps a constant minimum width (`md:min-w-[8rem]`) so the label swap never shifts the toolbar. Below `md` (icon-only) the ring is the only on-button cue; the tooltip carries the words.
- Tooltip lines while cooling: line 1 per kind, "Just synced. You can sync again in 8s." (manual) or "Outlook asked us to wait. You can sync again in 1m 20s." (backoff); line 2, existing status tooltip text if any. Time formatting: under 60s `8s`; 60s and over `1m 20s`.
- The ring and label tick once per second from a single `setInterval` owned by the control while a cooldown is active (cleared on unmount and when it ends). **Never** put the countdown in the `role="status"` live region (Phase 3 rule: announce per state change, not per tick). `aria-label` stays "Sync Outlook meetings" (contains the visible word "Sync", label-in-name); add `aria-describedby` to an `sr-only` span holding the current hint (it is not a live region).
- When the cooldown ends the button returns to idle with no announcement and no animation beyond the icon swap.
- Reconnect/Connect variants and the status text are unchanged. The amber "Outlook unavailable, retry later" status stays, and its Sync tooltip now also states the wait.
