## Summary

Phase 3.1 is a front-end-only phase: no new endpoints, no new npm packages, no migrations. Everything needed already exists in the repo (`reka-ui` 2.10.3 with `HoverCard`, `@vueuse/core` 14.4.0 with `useEventListener`/`useMediaQuery`/`useIntervalFn`, Vitest 4 + happy-dom 20, Playwright 1.62). The work splits into six loosely coupled areas, and the cooldown (UX-06) touches only fork files, so it can run in parallel with everything else.

The two structural decisions are: (1) **zoom = a persisted `slotHeight` (px per grid slot, default 25)** that replaces the `SLOT_HEIGHT` constant at its 4 composable call sites and 2 template sites. Every snap formula in the repo has the shape `(minutes / slotMinutes) * SLOT_HEIGHT` and already has the settings object `s` in scope, so each replacement is one token and snap maths stays correct by construction. "Grid Scale" keeps its meaning (minutes per slot, line density) and today's behaviour at the default zoom is unchanged. (2) **Meeting right-click = a third branch of the single core context menu**, fed by a new `context-menu-overlay` slot and a `contextMenuOpen` slot prop passed to the overlay. This keeps one `contextMenuOpen` flag, which the existing `guardedSlotPointerDown` guard depends on, and lets one watcher close every hover card and panel whenever the menu opens (D-06) without per-case wiring.

Three non-obvious traps shape the plans: the existing `watch(calendarSettings, emitDatesChange, { deep: true })` would fire a dates-change on every zoom step; a modal reka context menu sets `body { pointer-events: none }` but the ghosts carry an explicit `pointer-events-auto`, so ghosts (and a hover card) stay hoverable while the menu is open; and `HoverCardTrigger` + `PopoverTrigger` on the same element both write `data-state`, which the ghost's `data-[state=open]` ring styling reads.

**Primary recommendation:** Add `showWeekends` and `slotHeight` to `CalendarSettings` (sanitised through the function form of `mergeDefaults`), zoom by stepping `slotHeight` from a non-passive wheel listener on the calendar root with a ratio-based scroll anchor, use reka `HoverCard` (controlled `open`, gated on `!panelOpen && !contextMenuOpen`) for the hover details, add a meeting branch to the core context menu through a slot, and start the visible cooldown only for forced (manual) syncs and server back-off.

### Pattern 1: `slotHeight` zoom model (all snap maths stay correct)

**What:** `CalendarSettings.slotHeight` (px per grid slot, default `SLOT_HEIGHT` = 25). Every px<->minutes conversion becomes `(x / s.slotHeight) * s.slotMinutes`. Zoom steps change only `slotHeight`; Grid Scale changes only `slotMinutes`; each is independent and today's look is the default.

**Why it is safe:** the 4 composables already compute against `SLOT_HEIGHT` with the settings object in scope. Verbatim call sites [VERIFIED by Read this session]:

- `useCalendarGrid.ts:30` `const totalGridHeight = computed(() => slots.value.length * SLOT_HEIGHT);`
- `useCalendarGrid.ts:46` `return (minutes / s.slotMinutes) * SLOT_HEIGHT;`
- `useCalendarGrid.ts:51` `return (px / SLOT_HEIGHT) * s.slotMinutes + s.startHour * 60;`
- `useEventDrag.ts:55` `dragVisibleDurationMinutes.value = (dayEvent.height / SLOT_HEIGHT) * s.slotMinutes;`
- `useEventDrag.ts:72` `const segmentTopMinutes = (dayEvent.top / SLOT_HEIGHT) * s.slotMinutes;`
- `useEventDrag.ts:202` `const currentTopMinutes = (dragCurrentTop.value / SLOT_HEIGHT) * s.slotMinutes;`
- `useEventResize.ts:43` `const snapPx = (s.snapMinutes / s.slotMinutes) * SLOT_HEIGHT;`
- `useSlotSelection.ts:41` and `:62` `const snapPx = (s.snapMinutes / s.slotMinutes) * SLOT_HEIGHT;`
- `TimeEntryCalendar.vue:594` and `:636` `:style="{ height: SLOT_HEIGHT + 'px' }"` (time-axis rows and lane rows)

`grep -rn SLOT_HEIGHT resources/js e2e` finds no other consumer (the e2e suite reads slot height from the DOM via `getBoundingClientRect`, not from the constant). Everything else (events, ghosts, activity boxes, now-indicator) goes through the `minutesToPixels` closure, which reads `calendarSettings.value`, so it re-renders reactively on a zoom step.

**Steps and limits (discretion):** `SLOT_HEIGHT_STEPS = [16, 20, 25, 32, 40, 50, 64, 80]` px (ratio 1.25-1.28, all integers, so row borders stay crisp; 25 is the default and sits in the middle). `nextSlotHeight(current, dir)` snaps a stored off-grid value to the nearest step first, then moves one step and clamps. Consider a floor so the hour label does not collide with the next label at Grid Scale 60 min (a slot height under about 20 px with 60 min slots gives 20 px/hour; hour labels are `text-[0.8125rem]` with `pt-2`). `[ASSUMED]` limits; tune visually.

**Anchoring (ratio form, no minute maths needed):**
```ts
// off = pointer distance from the scroller's top edge, scrollTop before the change
function anchoredScrollTop(scrollTop: number, off: number, oldH: number, newH: number): number {
    return Math.max(0, (scrollTop + off) * (newH / oldH) - off);
}
```
Apply after `await nextTick()` (the grid height changes with the zoom step; setting `scrollTop` before the DOM updates is clamped to the old scroll height). `clientYToGridPixels` in `useCalendarGrid.ts` already derives grid px from `scroller.getBoundingClientRect().top` and `scrollTop`, so the same inputs are available. The sticky day header sits **outside** the scroller (`fc-header-scroll`, sibling above `.fc-scroller`), so `off = clientY - scrollerRect.top` is right.

### Pattern 2: Non-passive wheel/pinch listener on the calendar root

**What:** one `useEventListener(rootRef, 'wheel', handler, { passive: false })`. In the handler: `if (!(e.ctrlKey || e.metaKey)) return;` (plain wheel stays native scroll, D-07), else `e.preventDefault()` and step the zoom.

- **Pinch on trackpads arrives as a `wheel` event with `ctrlKey: true`** in Chrome (preventDefault stops page zoom) and, per a 2024 W3C thread, in Firefox and Safari too, "mostly undocumented but interoperable" [CITED: web search summary of Chromium blink-dev PSA "ctrl+mousewheel events can now be overridden" and W3C public-webapps 2024-10 thread; not independently reproduced]. Safari historically used non-standard `gesturestart/gesturechange`; treat Safari pinch as best-effort (`[ASSUMED]`, see Open Questions). Playwright CI covers Chromium and Firefox only (`playwright.config.ts`), not WebKit.
- **Passive default:** since Chrome 73 wheel listeners on `window`/`document`/`body` default to passive, so `preventDefault` is ignored there [CITED: developer.chrome.com/blog/scrolling-intervention-2]. Listening on an element (`rootRef`) with an explicit `{ passive: false }` is both required for safety and cheap. Attach to `rootRef` (the `.fc` element including the sticky header), not only the scroller, so Ctrl+wheel over the header does not page-zoom either. The toolbar above stays browser-native (acceptable).
- **Accumulator (steps, one gesture = one or a few steps):** normalise `deltaY` by `deltaMode` (0 px, 1 lines x 40, 2 pages x 800), accumulate, fire one step per +/-50 of accumulated delta, reset the accumulator on a sign change or after about 150 ms idle. A mouse notch (|deltaY| of 100 in Chrome, 3 lines in Firefox = 120) yields one step; a pinch yields several small deltas summing to a step. Thresholds `[ASSUMED]`, expose as constants so tests can drive them. Direction: `deltaY < 0` zooms in (larger slots), matching browser pinch-out.
- **Do not** reach `calendarSettings` writes at wheel frequency: only write when the step actually changes (steps are discrete), so `useLocalStorage` writes at most once per step.

### Pattern 3: Weekend hiding

Insert one filter in `viewDays` after the 7-day build, driven by a getter so it is reactive:

```ts
// useCalendarNavigation.ts (additive): callbacks.showWeekends?: () => boolean
const days = ...7 days built from weekStart...;
return callbacks.showWeekends?.() === false ? days.filter((d) => d.day() !== 0 && d.day() !== 6) : days;
```

Facts verified in source this session:

- `numDays = activeView.value === 'timeGridWeek' ? 7 : 1` (`useCalendarNavigation.ts:20`); the week start comes from the user setting and can be **any** weekday (`getWeekStartDayNumber` maps sunday..saturday, `utils/settings.ts`). With Monday/Sunday/Saturday starts the visible days are contiguous. With another start (e.g. Wednesday) hiding leaves a **non-contiguous** set (Wed, Thu, Fri, Mon, Tue). That is fine because the emitted range stays a superset: `emitDatesChange` sends `start = days[0]`, `end = days[last] + 1 day` (`:48-49`). Hidden days' entries are fetched but never rendered, because `eventsByDay`, `dailyTotals` and the grid loop `viewDays`. Header totals therefore exclude hidden days (call this out in the UI copy or accept it).
- **Meetings range is unaffected:** `weekBucket(start, firstDay)` (`useOutlookMeetings.ts:91`) rebuilds the 7-day bucket from `start`'s offset to the user's week start, and the `bucket` computed uses `calendarStart` only (`:192`). Hiding weekends never changes the bucket key, so no extra sync or fetch. `visibleCount` filters meetings against `[calendarStart, calendarEnd)`, so weekend-only meetings are not counted while hidden (desirable: "no meetings" status stays truthful).
- `dayOverlayLane(dayStr, ...)` is called per rendered day, so hidden days cost nothing.
- Existing `watch(calendarSettings, () => emitDatesChange(), { deep: true })` (`TimeEntryCalendar.vue:363-369`) is what re-emits the range when `showWeekends` flips (good) **but it also fires on every zoom step** (see Pitfall 1): narrow it.
- Day view: hidden weekend day navigation. Recommended: Prev/Next in day view skip hidden days; a day view that is already on a hidden day (user switched view or deep link) still renders that day.
- **Deep link trap:** `initialDate` ("Fix in calendar") on a hidden Saturday/Sunday would open a week with the target day missing. Recommended rule: when `initialDate` falls on a hidden day, start in `timeGridDay`.
- Cross-day drag-selection across a hidden weekend (Fri -> Mon) creates one multi-day entry spanning the hidden days (intermediate-day logic only knows visible columns: `useSlotSelection.ts:160`, `useEventResize.ts:208`). Accept and note, or clamp selection to contiguous visible days; low frequency.

### Pattern 4: Hover details with `HoverCard`, coexisting with the click Popover

reka `HoverCard` facts [VERIFIED: node_modules/reka-ui/dist/HoverCard/*.js read this session]:

- `HoverCardRoot` defaults: `openDelay` 700, `closeDelay` 300, `enableTouch` false. Open state is a controlled-or-uncontrolled `useVModel` (`passive: props.open === void 0`), so passing `:open` makes the parent authoritative and `update:open` is emitted for every request.
- `HoverCardTrigger` (`as: "a"` by default, use `as-child`): `onPointerenter`/`onPointerleave` are wrapped by `excludeTouch` (`utils.js`: `event.pointerType === "touch" ? void 0 : eventHandler()`), so touch never opens it. It also opens on **focus** (`onFocus -> rootContext.onOpen()`) and closes on blur.
- `HoverCardContentImpl`: content is a `DismissableLayer` (`disable-outside-pointer-events: false`), has a grace area so the pointer can travel from trigger to content (needed for Phase 4 buttons), strips `tabindex` from tabbable descendants (`tabbable.setAttribute("tabindex", "-1")`), dismisses on Escape, and dismisses on a **capturing window scroll** whose target contains the trigger (so scrolling or scroll-anchoring after a zoom step closes it).

Coexistence rules to implement:

1. Controlled `open`: `:open="hoverOpen"` with `@update:open="(v) => (hoverOpen = v && !panelOpen && !contextMenuOpen)"`. This drops the focus-triggered re-open that follows a click (click focuses the ghost; the delayed `onOpen` fires after the panel is open) and any hover while the context menu is open.
2. Click on the ghost: the hover card's `DismissableLayer` sees `pointerdown` outside (document listener, no button filter) and dismisses; the Popover then opens on click.
3. Gate the whole hover card on `useMediaQuery('(hover: hover) and (pointer: fine)')` as belt-and-braces on top of `excludeTouch` (pen hover is allowed: `excludeTouch` filters only `touch`). Keep click-only on touch.
4. Delay: `open-delay` around 400 ms, `close-delay` 150-300 ms `[ASSUMED]` (the toolbar tooltip uses `:delay-duration="300"`).
5. **`data-state` collision:** `HoverCardTrigger` sets `data-state`, `PopoverTrigger` sets `data-state`, both `as-child` on the same ghost element, but the ghost styles the open-panel ring with `data-[state=open]:ring-2 data-[state=open]:ring-accent-500` (`OutlookGhostLayer.vue:159`). Vue's fallthrough merge lets the outer component's attrs override the inner root's, so the hover state can mask the popover state (`[ASSUMED]`, verify in a test). Mitigation: drive the open ring from the layer's own `openId === box.meeting.id` through a dedicated attribute/class (e.g. `data-panel-open`), not `data-state`, and add a Vitest assertion.
6. Keep one shared body component (`OutlookMeetingSummary.vue`) used by panel and hover card (subject, time row, organizer, online, dismissed eyebrow) so Phase 4 adds its action once through a slot. Distinct `data-testid` prefix for the hover card, since Phase 3 tests and e2e use `outlook-detail-*`.
7. WCAG 1.4.13 (content on hover or focus): HoverCard satisfies dismissable (Esc), hoverable (grace area), persistent; `[ASSUMED]` standard reference, not fetched here. Keyboard users keep Enter/Space -> panel.

### Pattern 5: Context-menu layering and the meeting menu

Facts [VERIFIED: reka-ui source read this session]:

- `ContextMenuTrigger.handleContextMenu` does `await nextTick(); if (!event.defaultPrevented) { handleOpen(event); event.preventDefault(); }` (it also long-press-opens on touch/pen through `handlePointerDown`).
- Modal menu content passes `disable-outside-pointer-events` = menu open (`Menu/MenuRootContentModal.js:121`), and `DismissableLayer` then sets `body.style.pointerEvents = "none"` (`DismissableLayer.js:88`). Descendants inherit `none`, **except elements with an explicit value**: the ghost has `pointer-events-auto` (`OutlookGhostLayer.vue:159`) and `ContextMenuTrigger` forces `pointerEvents: "auto"` on the grid. So while the menu is open the ghosts still receive `pointerenter`, and a hover card can open on top of or beside the menu. This (not DOM order) is the realistic route to "tooltip over the menu". Closing on open and gating the hover card on `contextMenuOpen` removes it.
- `DismissableLayer` pointerdown-outside has no `button` filter (`DismissableLayer/utils.js` `handlePointerDown`), so a right-click anywhere outside a Popover or HoverCard already dismisses it. The gap is a right-click on the **same ghost that owns the open Popover**: `PopoverContentNonModal` ignores outside interactions that land on its trigger (`Popover/PopoverContentNonModal.js`: `const targetIsTrigger = unref(rootContext).triggerElement.value?.contains(target); if (targetIsTrigger) event.preventDefault();`, [VERIFIED: read this session]), so the panel stays open under the menu. The `contextMenuOpen` watcher below covers this case without special-casing.
- All wrappers portal at `z-50` (`popover/PopoverContent.vue`, `tooltip/TooltipContent.vue`, `context-menu/ContextMenuContent.vue`); equal z-index means DOM order decides, so rely on closing, not on stacking.

Recommended wiring (core: 3 small additive edits; fork: 2 files):

Reset the new ref in the other two branches. (Current code: `useContextMenu.ts:46` `const eventEl = target.closest<HTMLElement>('[data-event-id]');`, with the no-entry path producing the empty-slot menu, which is the 03-05 carry-over.)

### Pattern 6: Cooldown only for manual syncs and server back-off

Current code [VERIFIED by Read this session]: `useOutlookMeetings.ts:366` `extendCooldown(Math.max(SYNC_COOLDOWN_MS, backoff));` runs after **every** settled sync in `runPending`, including debounced automatic syncs from `watch(() => bucket.value?.key, ... requestSync(false))`. `target.force` already distinguishes manual (`requestSync(true)` from the button) from automatic.

Change (fork file only):

```ts
// useOutlookMeetings.ts, after the settled sync
const manualCooldown = target.force ? SYNC_COOLDOWN_MS : 0;
const cooldown = Math.max(manualCooldown, backoff);   // backoff already 0 unless throttled/unavailable
if (cooldown > 0) extendCooldown(cooldown);
```

Behaviour that must hold (all in `useOutlookMeetings.test.ts`, which needs new cases and one inversion):
- Automatic navigation sync -> `canSync` true again as soon as `isSyncing` clears. While it is in flight `canSync` is false (`:271` includes `!isSyncing.value`), so the button is briefly disabled; expected and acceptable.
- Manual sync -> 10 s cooldown (existing test "is disabled for 10 s after a settled sync and ignores a forced sync meanwhile" keeps passing if it uses `requestSync(true)`).
- `throttled`/`unavailable` with `retry_after`, route-level 429 `Retry-After`, and a read response `retry_after` (the `watch` on `dataUpdatedAt`, `:285`) still extend the cooldown even for automatic syncs (server back-off, D-08).
- Edge: `pending.force` is sticky across merged requests (`:385`), so an automatic sync that had a manual click merged into it counts as manual. Correct.

**Visible countdown:** `now` is only advanced by a single timeout at the end of the cooldown (`cooldownTick`), so a countdown needs a ticker. Add `cooldownRemainingSeconds` (computed from a `now` ref advanced by `useIntervalFn(..., 1000, { immediate: false })`, started in `extendCooldown`, paused when `now >= cooldownUntil` and on unmount). Under Vitest fake timers `Date.now()` is faked too, and `advanceTimersByTimeAsync` drives `setInterval`.

**Presentation:** the Sync button already sits in a `<span class="inline-flex">` that is the `TooltipTrigger` and the Button class includes `disabled:pointer-events-none` [VERIFIED: `packages/ui/src/Buttons/index.ts:6`], so the tooltip works on a disabled button. Add (a) a small SVG progress ring around/in place of the icon (`aria-hidden`, `motion-safe` transition, no per-second layout), (b) tooltip line "Available again in N s" (new label with `:seconds`, add to `lang/en` + `lang/es` + `types.ts`; `MicrosoftLangTest` enforces key and placeholder parity). Do **not** announce every tick through `aria-live`: keep `aria-label` stable, announce once ("Sync cooling down") via the existing polite region, and let the tooltip carry the live number.

### Anti-Patterns to Avoid
- **Scaling the grid with CSS `transform`/`zoom`:** every snap path reads `getBoundingClientRect` (`getDayColumnBounds`, `clientYToGridPixels`); transforms break them.
- **A second zoom constant next to `SLOT_HEIGHT`:** leaves 9 stale call sites. Replace usages, keep the exported name as the default.
- **Putting the wheel listener on `window`/`document`:** passive-by-default trap, and it would hijack Ctrl+wheel app-wide.
- **Reading `data-state` to style the open panel** once `HoverCardTrigger` shares the element.
- **Relying on z-index/DOM order to keep the menu on top.**
- **Per-ghost nested `ContextMenu` for the meeting menu** (see Alternatives).
- **Using raw colours for the solid meeting fill:** Phase 3.2 reworks the palette; use theme tokens (D-02, Claude's discretion note).
- **Treating `disabled` as the only cooldown signal for screen readers:** also expose remaining time as text.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

| Interval for the countdown | ad-hoc `setInterval` | `useIntervalFn` (pause/resume) | Cleanup on unmount, testable with fake timers |
| Settings sanitising on read | scattered `?? default` | one `sanitizeCalendarSettings()` passed as the **function form** of `mergeDefaults` | `@vueuse/core` calls `mergeDefaults(storedValue, defaults)` when it is a function (`dist/index.js:1986`); one place to clamp `slotHeight` and coerce `showWeekends` |
| Gesture/zoom library | `@use-gesture`, `normalize-wheel` | a ~30-line pure accumulator in `calendarZoom.ts` | Only one axis, one step list; a dependency would also need legitimacy gating |

**Key insight:** the risky part of zoom is not the gesture, it is the px<->minute maths scattered over four composables. Make `slotHeight` a setting that those formulas already read, and the gesture becomes a thin writer of one number.

## Common Pitfalls

### Pitfall 1: Zoom triggers a range re-emit (and a fetch cascade)
**What goes wrong:** `watch(calendarSettings, () => emitDatesChange(), { deep: true })` (`TimeEntryCalendar.vue:363-369`) emits `dates-change` for every settings write; each zoom step creates new `Dayjs` objects in `Calendar.vue`'s `calendarStart`/`calendarEnd`.
**Why it happens:** the watch was written when settings could only change through the popover.
**How to avoid:** watch only the fields that change the visible range or the day set (`showWeekends`, and `startHour`/`endHour` if the current behaviour must be preserved), or exclude `slotHeight`: `watch(() => [s.showWeekends, s.startHour, s.endHour], ...)`.
**Warning signs:** network calls or a flash while zooming; a Vitest spy on `dates-change` counting more than one emit per setting change.

### Pitfall 2: `scrollTop` set before the DOM grows
**What goes wrong:** the time under the pointer jumps when zooming in near the bottom.
**How to avoid:** set `scrollTop` after `await nextTick()`; use the ratio formula; clamp at 0.
**Warning signs:** the Playwright anchor assertion fails only for zoom-in at late hours.

### Pitfall 3: Page zoom still happens on some surfaces
**What goes wrong:** Ctrl+wheel over the toolbar, the portalled panel or a hover card zooms the whole page.
**How to avoid:** listener on `rootRef` with `{ passive: false }`; accept the toolbar (outside `rootRef`) or extend to the page container; assert `event.defaultPrevented` in e2e for the calendar area.

### Pitfall 4: A modal menu does not make ghosts inert
**What goes wrong:** with the context menu open, moving over another ghost opens a hover card (ghosts keep `pointer-events-auto`).
**How to avoid:** gate the hover card on `!contextMenuOpen`; the same flag closes anything already open (Pattern 5).

### Pitfall 5: `data-state` collision between HoverCardTrigger and PopoverTrigger
See Pattern 4 item 5. Add a dedicated attribute and a regression test that opens the panel while the hover card is mounted.

### Pitfall 6: Hover card re-opens after click via focus
**What goes wrong:** pointerdown focuses the ghost, `HoverCardTrigger.onFocus` starts the open timer, and the card appears next to the freshly opened panel.
**How to avoid:** the controlled `open` guard (`!panelOpen`) in Pattern 4 item 1.

### Pitfall 7: Required settings fields break existing typed fixtures
**What goes wrong:** `CalendarSettings` fixtures in `OutlookGhostLayer.test.ts` (`const settings: CalendarSettings = { snapMinutes: 15, startHour: 0, endHour: 24, slotMinutes: 15 }`), `OutlookDismissedSetting.test.ts` and `useContextMenu.test.ts` fail `vue-tsc` (CI `npm-typecheck.yml`) when `showWeekends`/`slotHeight` become required, and untyped fixtures yield `NaN` heights at runtime.
**How to avoid:** update the three fixtures in the same plan as the type change (grep for `slotMinutes` finds all: also `useCalendarGrid.ts`, `useEventDrag.ts`, `useEventResize.ts`, `useSlotSelection.ts`, `CalendarSettingsPopover.vue`, `TimeEntryCalendar.vue`). Keep fields required (types are cleaner; `mergeDefaults` guarantees them at runtime).

### Pitfall 8: Stored settings are not validated
**What goes wrong:** `mergeDefaults: true` is a shallow `{...defaults, ...stored}` (`@vueuse/core dist/index.js:1984-1990`), so a corrupted or hand-edited `slotHeight` (`0`, `"abc"`) reaches layout maths (`NaN` or division by zero) and persists.
**How to avoid:** `sanitizeCalendarSettings` clamps `slotHeight` to the step range and coerces `showWeekends` to boolean; apply it through the function form of `mergeDefaults`. Note `mergeDefaults` only runs on the initial read, not on `storage` events from another tab (`read(event)` branch), so also clamp in `minutesToPixels`-adjacent code or in the zoom setter.

### Pitfall 9: Existing e2e tests assume today's grid
`e2e/calendar.spec.ts` and `calendar-settings.spec.ts` read slot height from the DOM (`getSlotHeight`) and clear `solidtime:calendar-settings` in `beforeEach`; they stay valid as long as the default `slotHeight` is 25 and weekends default to shown. Tests that depend on "today" being visible (`.fc-day-today.fc-col-header-cell`) must never run with weekends hidden on a weekend.

### Pitfall 10: Content tiers of the meeting block now move with zoom
`OutlookGhostLayer.vue` shows the time line at `box.height >= TIME_LINE_MIN_HEIGHT` (40) and inline time at 24-39 (day view only). Heights now vary 16..80 px per slot, so a 30 min block ranges from about 8 px (clamped to `GHOST_MIN_HEIGHT` 16) to 160 px. UX-02's "subject on up to two lines when height allows" must be driven by `box.height` (already the case), and Playwright/Vitest cases should cover at least min, default and max zoom.

## Code Examples

### Pure zoom helpers (unit-testable without a DOM)
```ts
// calendarZoom.ts (new, core, additive). Values are proposals, not repo facts.
export const SLOT_HEIGHT_STEPS = [16, 20, 25, 32, 40, 50, 64, 80] as const;

export function nextSlotHeight(current: number, direction: 1 | -1): number {
    const steps = SLOT_HEIGHT_STEPS;
    let idx = 0;
    for (let i = 1; i < steps.length; i++) {
        if (Math.abs(steps[i]! - current) < Math.abs(steps[idx]! - current)) idx = i;
    }
    const next = Math.min(steps.length - 1, Math.max(0, idx + direction));
    return steps[next]!;
}

export function normalizeWheelDelta(e: { deltaY: number; deltaMode: number }): number {
    return e.deltaMode === 1 ? e.deltaY * 40 : e.deltaMode === 2 ? e.deltaY * 800 : e.deltaY;
}
```

### Wheel handler skeleton
```ts
// useWheelZoom.ts (new). Source pattern: MDN/Chromium wheel+ctrlKey; non-passive per developer.chrome.com
useEventListener(rootRef, 'wheel', async (e: WheelEvent) => {
    if (!(e.ctrlKey || e.metaKey)) return; // plain wheel = native scroll (D-07)
    e.preventDefault(); // blocks browser page zoom
    const dir = accumulate(normalizeWheelDelta(e), e.timeStamp); // returns -1 | 0 | 1
    if (dir === 0) return;
    const scroller = scrollerRef.value;
    if (!scroller) return;
    const oldH = settings.value.slotHeight;
    const newH = nextSlotHeight(oldH, dir === -1 ? 1 : -1); // deltaY < 0 = zoom in
    if (newH === oldH) return;
    const off = e.clientY - scroller.getBoundingClientRect().top;
    const top = scroller.scrollTop;
    settings.value = { ...settings.value, slotHeight: newH };
    await nextTick();
    scroller.scrollTop = anchoredScrollTop(top, off, oldH, newH);
}, { passive: false });
```

**What happy-dom cannot do (route these to Playwright or manual):** layout and hit-testing (`getBoundingClientRect` is zeros; `test-setup.ts` fakes `offsetWidth/Height` only), CSS (no Tailwind stylesheet: colours, `color-mix`, stacking/z-order, `pointer-events` inheritance, "obscured by" checks), real scrolling and scroll anchoring (set `scrollTop` and a mocked `getBoundingClientRect` on a fake scroller for unit tests of the maths only), `matchMedia` hover/pointer evaluation (mock `window.matchMedia`), native default actions (`preventDefault` only observable as `defaultPrevented` on a dispatched cancelable event), native event microtask ordering (a synthetic `dispatchEvent` runs microtasks after dispatch, unlike user input, which matters for reka's `await nextTick()` + `defaultPrevented` check in `ContextMenuTrigger`), floating-ui placement.

**Playwright specifics:**
- Wheel: `page.mouse.move(x, y); await page.keyboard.down('Control'); await page.mouse.wheel(0, -100); await page.keyboard.up('Control');` then assert slot lane height (`.fc-timegrid-slot-lane` `getBoundingClientRect().height`) and `localStorage` `slotHeight`. Pinch is the same code path (ctrlKey wheel); simulate with several small `WheelEvent`s via `page.evaluate` (`deltaY: -4`, `ctrlKey: true`, `cancelable: true`). Read `defaultPrevented` from a bubbling `window` listener installed before the gesture (it runs after the calendar's handler). Anchor check: record `data-time` of the `.fc-timegrid-slot-lane` under the pointer (`document.elementsFromPoint`) before and after.
- Hover: `locator.hover()` then `expect(page.getByTestId('outlook-hover-card')).toBeVisible()` (opens after the delay; Playwright auto-waits). Touch: a `test.use({ hasTouch: true, isMobile: true })` describe with `locator.tap()` (A5).
- Context menu: `locator.click({ button: 'right' })` (existing pattern at `calendar.spec.ts:46`, `:444`); clicking a menu item is itself the "not obscured" proof because Playwright hit-tests the target before clicking.
- Meetings are injected through `window.__TEST_SET_OUTLOOK_MEETINGS__` (existing `injectMeetings` helper in `e2e/outlook-ghosts.spec.ts`); no Microsoft credentials in CI. Put new view-option specs in a new `e2e/calendar-view-options.spec.ts` so the three parallel waves do not collide in one file.

## Security Domain

`security_enforcement` is enabled (ASVS level 1, `block_on: high`). The phase adds no endpoints, no auth changes and no new data flows, so the surface is small.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XSS via Graph-supplied subject/organizer in the new hover card and menu | Tampering | Text interpolation only (Phase 3 rule), reuse the shared summary component; test with HTML subject (the Phase 3 tests already do this for the panel) |
| Open redirect / `javascript:` via `web_link` in the new "Open in Outlook" menu item | Tampering | `safeHttpsUrl()` (`m365/calendar/safeUrl.ts`) gate; `noopener,noreferrer` |
| Tampered `solidtime:calendar-settings` producing NaN/zero layout (client-side DoS of the calendar) | Denial of service | Sanitise and clamp on read (Pitfall 8) |
| Context menu action acting on the wrong meeting (stale element) | Tampering | Resolve the meeting by `data-ghost-id` at open time against the current `meetings` list; ignore if missing |
| Automatic sync cooldown removal enabling request floods | Denial of service | Server throttles and `retry_after` unchanged (D-08); automatic syncs keep the 400 ms debounce, the 60 s freshness skip and single-flight; only the manual button state changes |
